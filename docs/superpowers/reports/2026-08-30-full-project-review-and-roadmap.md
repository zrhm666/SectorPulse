## 需要优先修复的问题

### P1：定时任务几乎不会在真实轮询中到期

- 位置：`backend/src/sector_pulse/application/schedule_service.py:57-70`、`scheduler.py:39-41`
- 根因：`next_due()` 只返回 `>= now` 的候选时间，`poll_once()` 又只执行 `due <= current`。轮询在计划时间前会跳过；轮询在计划时间后会计算到下一天。除非恰好在计划时刻的零秒、零微秒调用，否则不会触发。
- 测试盲区：现有测试只在精确的 `16:00:00` 调用，因此未覆盖常规 10 秒轮询漂移。
- 影响：页面显示的自动调度能力在真实运行中基本失效。
- 建议：持久化并消费 `next_run_at`，使用“上次检查时间 < due <= 当前时间”的窗口语义；补充延迟 1–30 秒、进程暂停后补偿、周末和时区测试。

### P1：页面“立即运行”只创建任务记录，不启动真实工作流

- 位置：`backend/src/sector_pulse/application/task_run_service.py:35-51`、`web/src/pages/SchedulePage.tsx`
- 根因：手动触发只创建一个没有调度关联的 `task_runs` 记录。它没有调用 `ScheduledDataRunBridge.start()`，调度器也不会扫描并执行这类手动队列。
- 影响：用户点击“立即运行”后会进入一个长期停留在队列状态的任务详情页。
- 建议：把“计划触发”收敛为一个应用服务：原子创建 task run、启动 data run、建立链接并记录事件；调度触发和手动触发共用同一路径。

### P1：数据运行取消和进程重启会留下假运行状态

- 位置：`backend/src/sector_pulse/web/data_run_service.py:55-81,98-99`、`web/app.py:286-292`
- 根因一：`cancel()` 只取消内存中的 `asyncio.Task`，没有捕获 `CancelledError` 并将数据库状态写成 `CANCELLED`。
- 根因二：已实现的 `mark_interrupted()` 从未在应用启动生命周期调用。进程崩溃或重启后，旧运行会永久停在 `FETCHING_*` 等活动状态，且活动状态不允许重试。
- 影响：总览持续显示“运行中”，用户无法可靠取消或恢复。
- 建议：让执行器在取消分支原子落库；启动时先将遗留活动态转换为 `INTERRUPTED`；为内容运行的 `RUNNING` 状态建立同类恢复规则。

### P1：审核自动保存存在 state/ref 时序竞态

- 位置：`web/src/hooks/useDraftAutosave.ts:60-64,140-164`
- 证据：默认并行测试中，“失焦立即保存”和“保存中追加新文本”曾失败；单文件/单 worker 时通过。
- 根因：`fieldsRef` 只在 React state updater 执行时更新。`change` 后紧接 `blur/flush` 时，`flush()` 可能仍读到旧 ref；保存完成后处理队列也依赖相同时序。
- 影响：极快失焦或高负载时，最后一次编辑可能延迟保存，状态提示与实际提交不一致。
- 建议：在事件入口同步更新 ref，再提交 React state；将队列状态机提取为可独立测试的 reducer/控制器，并增加快速 blur、连续输入、失败重试和版本冲突压力测试。

### P1：当前 PostgreSQL 配置不可连接，且运行时桥接结构不适合继续扩展

- 当前状态：`.env` 选择 PostgreSQL，但本机 5432 拒绝连接；按当前“禁止静默回退”策略，应用会在启动时失败。
- 架构位置：`backend/src/sector_pulse/storage/runtime_bundle.py:55-83,94-152`
- 结构问题：同步应用服务通过 `BlockingAsyncRepository` 为几乎每个 PostgreSQL 调用创建线程和短事件循环，数据库使用 `NullPool`；bundle 字段大量声明为 `object`。
- 证据：Mypy strict 共 198 个错误，很多来自仓储类型、可选 engine 和 SQLite/PostgreSQL 契约不一致。
- 影响：并发上升后线程/连接开销和阻塞风险增加；接口调整难以被类型检查保护。
- 建议：先确认 PostgreSQL 服务与迁移；再定义明确 Repository Protocol，选择“全异步应用服务”或“同步 SQLAlchemy 仓储”中的一种，不再长期维持每调用跨线程桥接。

### P1：窄屏关闭的侧边栏仍可能进入键盘焦点顺序

- 位置：`web/src/layout/SidebarNav.tsx:22-54`、`web/src/styles/responsive.css`
- 根因：关闭状态仅用 `transform` 移出视口，没有 `inert`/焦点禁用；内部链接始终在 DOM 和 tab 顺序中。
- 影响：键盘和屏幕阅读器用户可能聚焦到看不见的导航链接，违反可预期焦点顺序。
- 建议：窄屏关闭时为导航容器设置 `inert`（并提供兼容处理）和正确的可访问隐藏状态；打开后使用完整焦点陷阱，关闭时恢复菜单按钮焦点。

## 次要问题和工程债务

### P2：React Router 6.30.4 处于有公告且不再受支持的版本线

- `npm audit --omit=dev` 报告 2 个 moderate 告警。
- SectorPulse 使用 `<BrowserRouter>` Declarative Mode，不使用 SSR/RSC，降低了部分公告的实际可利用性；所有内部导航也主要由服务端 UUID 构造。
- 仍建议规划升级到受支持的 React Router 7/8，并建立不接受未验证外部重定向路径的测试。不要仅为消除审计输出而盲目降级依赖。

### P2：端到端测试允许后端代理错误，且命令无法干净退出

- 39 项 Playwright 断言通过，但 Vite 多次报告 `ECONNREFUSED 127.0.0.1:9000`。
- 测试结束后 preview 子进程未关闭，必须手动中止 runner。
- 建议：E2E 要么统一 route mock 并禁止未 mock 的 `/api`，要么同时启动 Fixture 后端；将 console error、page error、失败网络请求作为测试失败；修正 Windows webServer 生命周期。

### P2：严格类型门禁没有进入可交付状态

- `pyproject.toml` 已配置 strict mypy，但仓库当前有 198 个错误，说明它不是有效门禁。
- 建议按模块逐步建立 baseline，先处理 `storage/runtime_bundle`、调度、数据写作桥接和 `web/app.py`，最终在 CI 中强制为零。

### P2：核心入口和查询文件过大

- `web/app.py` 1171 行；`data_run_workbench_queries.py` 558 行；`run_service.py` 485 行；旧 `styles.css` 604 行且与新分层 CSS 同时加载。
- 影响：路由、依赖装配和业务规则耦合，样式来源难追踪，后续功能扩展更易回归。
- 建议：按 operations、data-runs、review、schedules、legacy-runs 拆 APIRouter；逐步迁移并删除 legacy CSS。

### P2：减少动态样式采用全局 `0.01ms` 清零

- 位置：`web/src/styles/base.css:28-33`、`styles.css:601-602`
- 影响：满足“减少动态”的表面要求，但也移除了对焦点、展开和状态变化有帮助的低强度反馈。
- 建议：仅禁用装饰性位移/循环动画，保留无移动的即时状态反馈。

### P3：README 的 License 说明与仓库事实冲突

- `LICENSE` 已存在且为 MIT；`README.md:308` 仍写“未包含开源许可证文件”。
- 建议：改为明确链接 MIT License。

### P3：依赖和测试提示

- FastAPI TestClient 使用的 Starlette/httpx 组合有弃用警告。
- Vite 测试输出提示 React Babel 插件仍设置已弃用的 esbuild 选项。
- 本轮没有安装 Python `pip-audit`，因此 Python 依赖漏洞扫描仍需补做。

## 值得保留的优点

- Live 数据和 LLM 有显式 consent；Fixture 不会伪装成真实 Provider。
- 数据、证据、草稿、版本、审核和导出形成可审计链路。
- 失败、降级、空结果和加载状态大多能被真实区分。
- 响应式工作台不是简单缩放，表格、抽屉和多栏审核区有明确适配。
- 后端非 Live 覆盖率 81%，领域模型和 SQLite 路径覆盖较强。
- Docker/本地启动默认绑定回环地址，符合单用户本机边界。

## 功能增强路线图

### Stage 0：可靠性与工程底座（必须先做）

1. 修复定时触发窗口、手动触发执行链和调度异常隔离。
2. 修复取消、重启恢复和活动运行超时治理。
3. 修复自动保存竞态与前端测试不稳定。
4. 恢复 PostgreSQL 实库并补跑全部 PostgreSQL 集成测试。
5. 类型化 Repository Protocol，拆分 `web/app.py`，升级 React Router。
6. 建立一条可重复的 CI：Ruff、Mypy、Pytest、Vitest、Build、Playwright、依赖审计。

### Stage 1：日常研究效率（最高业务价值）

#### 1. 关注板块与变化雷达

- 用户维护关注行业/概念板块。
- 展示候选排名、涨跌幅、广度、换手率和新闻证据相对上次运行的变化。
- 只在出现“新证据、排名跃迁、质量降级、连续异常”时提醒，避免信息噪声。

#### 2. 运行对比与可解释评分

- 任意选择两次运行，对比候选排名、评分维度、新闻增删、来源质量和最终草稿。
- 将候选分数拆解为行情、活跃度、广度和新闻关联贡献，解释为什么入选/落选。
- 支持用户保存评分模板，但保留默认只读基线和版本记录。

#### 3. 审核效率增强

- 草稿版本 diff、证据决定批量操作、审核快捷键和明确的未保存变更保护。
- 对关键数字、公司名、板块名提供“证据覆盖率”和未验证事实清单。
- 退回时生成结构化修改任务，而不只是自由文本理由。

### Stage 2：证据质量与可观察性

#### 4. 新闻正文增强（合规优先）

- 对允许抓取的来源增加正文抽取插件；默认仍只保存元数据、摘要、内容哈希和短证据片段。
- 建立来源 allowlist、robots/条款备注、抓取失败原因和保留策略，不无条件存储整篇原文。
- 相似新闻聚类、多来源交叉确认、首发/转载识别和时间线展示。

#### 5. Provider 与 LLM 运营台

- 每个 Provider 的成功率、延迟、返回条数、字段完整率、最近错误和限流窗口。
- LLM 每阶段耗时、token、成本、重试、超时和模型结果质量。
- 系统状态页增加安全的“测试连接”操作，不展示密钥或完整连接串。

#### 6. 通知中心

- 本地桌面通知为默认；邮件/Webhook 作为显式配置的可选项。
- 只通知运行完成、失败、等待审核、数据源连续降级和预算接近上限。
- 通知携带本地详情链接，不携带敏感正文或连接信息。

### Stage 3：质量评估与运维

#### 7. Prompt Golden 与模型对比界面

- 仓库已经有 prompt golden 数据表/API，可补管理页面。
- 对同一固定输入比较模型/Prompt 版本，记录结构有效率、事实覆盖、审核问题和成本。
- Prompt 升级前必须通过 golden 集，防止线上写作质量静默回退。

#### 8. 历史复盘（不是交易回测）

- 基于当时已保存的快照重放候选和文章，不允许使用未来信息。
- 统计证据准确性、降级率、人工修改率和候选稳定性。
- 如展示后续 1/3/5 日表现，必须标明样本量、幸存者偏差和非投资建议，不将其包装为收益预测。

#### 9. 备份、恢复与数据生命周期

- 将现有 SQLite PowerShell 脚本升级为前端可见的运维向导。
- 增加 PostgreSQL `pg_dump/pg_restore` 流程、备份校验、恢复演练和数据保留策略。
- 提供按运行归档/清理，而不是直接裸删数据库记录。

## 暂不建议添加

- 自动交易、自动下单或收益承诺：偏离证据审核产品边界，风险远高于价值。
- 多租户、复杂账号权限：当前是本地单用户工具，除非准备部署给团队，否则成本过高。
- 泛化聊天机器人：容易绕开证据门禁。若以后增加问答，应只基于当前运行证据并强制引用。
- 为了“功能丰富”添加空按钮、假指标或不可执行的配置页。

## 推荐实施顺序

1. Stage 0：可靠性修复与 PostgreSQL/CI 验收。
2. Stage 1.1 + 1.2：关注板块、变化雷达和运行对比。
3. Stage 1.3：审核 diff、批量证据决定和未保存保护。
4. Stage 2.4 + 2.5：新闻证据质量与 Provider/LLM 可观察性。
5. Stage 3.7：Prompt Golden 管理和模型对比。
6. 最后再评估通知、历史复盘和完整运维中心。

每个 Stage 应单独完成设计文档、实施计划、迁移策略和验收，不把所有增强项塞进一次重构。
