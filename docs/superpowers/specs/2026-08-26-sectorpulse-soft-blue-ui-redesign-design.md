# SectorPulse 柔和蓝白运营后台重构设计

> 日期：2026-08-26
> 状态：已确认并实现
> 关联通用规范：[柔和蓝白运营后台 UI 系统](../../design/soft-blue-operations-ui-system.md)

## 1. 背景

SectorPulse 已具备运营总览、分析运行、数据工作台、审核工作台、定时任务、系统状态和影子验收等完整前端页面。当前界面功能可用，但视觉层级偏冷、页面密度缺少统一策略，部分页面仍呈现“通用后台模板”观感。

用户提供的参考界面具有暖白背景、清透蓝色、细描边圆角卡片、线性图标和宽松布局。用户确认采用其视觉语言，但不使用卡通吉祥物、花朵、云朵等装饰，并同意总览舒展、数据工作台紧凑的自适应密度方案。

## 2. 目标

- 建立覆盖全站的柔和蓝白视觉系统。
- 提升运营总览的亲和力和一眼可读性。
- 保持行情、新闻、证据和审核页面的工作效率。
- 统一按钮、卡片、表单、表格、状态、标签页和反馈组件。
- 保留全部现有业务能力、API、路由和交互语义。
- 支持桌面和窄屏，满足基础键盘操作与可访问性要求。

## 3. 非目标

- 不修改数据采集、LLM、审核、治理和调度业务逻辑。
- 不改变 API 路径和返回模型。
- 不引入卡通形象、插画背景或装饰性花草图形。
- 不把数据密集页面改造成大留白展示页。
- 不增加暗色主题。
- 不为视觉效果引入复杂动画或重型图表库。

## 4. 设计方向

### 4.1 视觉语言

- 主背景采用轻微偏暖的白色。
- 内容表面使用纯白与极浅蓝白两级。
- 主交互色使用清透亮蓝。
- 卡片依靠细边框、18px 左右圆角和极轻阴影塑形。
- 标题使用接近黑色的深灰，说明文字使用柔和蓝灰。
- 使用统一线性图标，不使用 Emoji。
- 状态继续使用绿色、琥珀色、红色和蓝灰色。

### 4.2 密度策略

`comfortable` 用于：

- 运营总览。
- 新建分析流程。
- 空状态和低频设置。
- 页面标题和主要指标卡。

`compact` 用于：

- 行情板块表格。
- 新闻记录和证据列表。
- 运行历史。
- 审核队列与正文编辑。
- 定时任务列表。

## 5. 信息架构

现有路由保持不变：

| 路由 | 页面 | 重构重点 |
|---|---|---|
| `/` | 运营总览 | 主次布局、指标卡、最近运行、运行条件 |
| `/runs` | 运行历史 | 筛选栏、状态、紧凑表格、主要操作 |
| `/runs/new` | 新建分析 | 步骤导航、选择卡、提交摘要 |
| `/runs/:runId` | 内容运行详情 | 摘要带、阶段状态、标签页、错误恢复 |
| `/data-runs/:runId` | 数据运行详情 | 采集摘要、工作台标签、行情与新闻密度 |
| `/review` | 审核工作台 | 三栏布局、正文阅读、证据和审批操作 |
| `/schedules` | 定时任务 | 摘要、创建表单、任务表格 |
| `/system` | 系统状态 | 连接与授权状态卡、刷新反馈 |
| `/shadow-acceptance` | 影子验收 | 进度摘要、历史表格、状态语义 |
| `/task-runs/:runId` | 任务运行 | 阶段时间线和错误恢复 |

## 6. 应用外壳

### 6.1 侧边栏

- 桌面宽度保持约 240px。
- 导航项增加统一线性图标。
- 选中项使用浅蓝背景和蓝色文字，圆角 12px。
- 品牌区域保留 `SectorPulse`，副标题使用较弱层级。
- 影子验收等低频入口仍保留，但通过导航分组降低视觉竞争。

### 6.2 顶部栏

- 高度约 64px。
- 保留产品上下文和必要的全局状态。
- 使用白色半透明或纯白表面与细边框，不使用明显阴影。

### 6.3 内容区

- 最大宽度约 1480px。
- 桌面左右内边距 32–40px。
- 数据工作台允许更宽内容区，避免表格列拥挤。
- 页面标题与首个内容区保持 24px 间距。

## 7. 通用组件

### 7.1 设计令牌

在 `web/src/styles.css` 顶部建立颜色、字体、间距、圆角、阴影和布局令牌。现有组件只能引用令牌，不继续散落新的相近色值。

### 7.2 页面标题

`PageHeader` 继续负责标题、说明和操作。主标题桌面 30–32px，数据详情页可使用 28px。操作区允许时间戳、刷新和主按钮，但同一页面只保留一个视觉主操作。

### 7.3 卡片与面板

`Panel` 作为主要内容容器，默认白底、细边框、18px 圆角。指标卡使用专用结构，不用普通 Panel 堆叠模拟。

### 7.4 按钮与表单

- 主按钮：亮蓝底白字。
- 次按钮：白底蓝灰边框。
- 幽灵按钮：透明背景。
- 危险操作：红色语义。
- 输入框、选择器和文本域统一高度、圆角、焦点环和错误提示。

### 7.5 状态与反馈

`StatusBadge` 保留业务状态映射，视觉改为更轻的胶囊标签。`InlineAlert`、全局通知、加载、空状态和确认弹窗统一到新令牌。

### 7.6 表格与列表

表格采用轻表头、横向分隔线和紧凑行高。名称与状态优先，ID 和技术字段降低层级。窄屏默认横向滚动，不强行把大表格拆成冗长卡片。

## 8. 页面设计

### 8.1 运营总览

布局采用“主要运行概览＋指标卡矩阵＋最近记录/运行条件”。

- 页首突出当前运营状态和新建分析入口。
- 指标卡展示运行总数、待审核、计划任务和系统就绪情况。
- 最近运行使用紧凑列表。
- 运行条件使用检查列表，异常项可直接进入系统状态页。

### 8.2 运行历史与新建分析

运行历史将筛选器收进轻量工具条，表格操作保持明确。新建分析维持三步流程，选择项改为清晰的选择卡；确认页集中展示模式、Provider、额度和数据影响。

### 8.3 数据运行工作台

- 顶部摘要采用连续分栏带，减少碎片化卡片。
- 阶段时间线使用蓝色进行中、绿色完成、红色失败和灰色未开始。
- “本次实际获取”保留独立层级，数据来源和覆盖范围可快速扫描。
- 标签页保持行情、候选、新闻、证据和质量之间的任务切换。
- 行情与新闻使用紧凑密度；新闻卡突出标题、摘要、来源、时间、关联查询和原文入口。

### 8.4 内容运行详情

摘要、时间线和标签页视觉与数据运行详情保持一致。失败状态显示明确错误和恢复入口；已生成草稿即使后续阶段失败，也应保留可访问入口。

### 8.5 审核工作台

桌面采用三栏：审核队列、草稿编辑、证据与治理。中栏获得最大宽度。右栏操作按“证据判断—治理结果—批准/退回”排序。窄屏依次纵向排列。

### 8.6 定时任务、系统状态与影子验收

三类页面共享摘要卡、表单、表格和状态组件。系统状态不显示密钥或连接串，只显示安全的就绪信息。影子验收保留业务状态，不因视觉重构恢复已取消的流程要求。

## 9. 交互与状态

- 页面加载保留稳定骨架，减少内容跳动。
- 长任务继续轮询，并显示最后更新时间。
- 错误信息包含对象、原因和下一步，不只显示“失败”。
- 空状态包含可执行入口。
- 所有主要按钮具备悬停、按下、焦点、加载和禁用状态。
- 标签页和弹窗支持键盘操作。
- 动画控制在 140–240ms，并支持减少动态偏好。

## 10. 响应式

- `>= 1280px`：完整侧边栏和多列布局。
- `960–1279px`：指标卡两列，缩减内容边距。
- `720–959px`：侧边栏收起，审核工作台改为纵向。
- `< 720px`：单列布局，关键按钮可全宽，表格横向滚动。

响应式调整不得隐藏关键操作、错误详情或状态信息。

## 11. 可访问性

- 保证正文、辅助文字和状态标签达到可读对比度。
- 所有交互元素有可见焦点环。
- 图标按钮提供可访问名称。
- 标签页、弹窗、通知和加载状态使用正确语义。
- 状态不只依靠颜色。
- 桌面点击目标至少 40px，窄屏至少 44px。

## 12. 技术边界

- React 路由、API 模块和业务请求逻辑保持不变。
- 优先重用现有 `PageHeader`、`Panel`、`StatusBadge`、`InlineAlert`、`EmptyState`、`LoadingState` 和 `ConfirmDialog`。
- 可以拆分过大的页面组件，但不得改变调用顺序和数据语义。
- 图标采用同一套本地线性 SVG 或轻量图标依赖，不混用多套来源。
- 不要求后端配合；只有现有 API 无法表达页面已经依赖的状态时才允许修复接口。

## 13. 实施阶段

### 阶段 1：视觉基础

- 令牌、全局排版和背景。
- 应用外壳、侧边栏、顶部栏。
- 通用组件和交互状态。

### 阶段 2：日常运营

- 运营总览。
- 运行历史。
- 新建分析。

### 阶段 3：数据与内容工作台

- 数据运行详情及子面板。
- 内容运行详情及标签页。
- 新闻、行情、证据和质量显示。

### 阶段 4：审核与管理

- 审核工作台。
- 定时任务。
- 系统状态、影子验收和任务运行。

### 阶段 5：完整验收

- 前端自动化测试。
- TypeScript 编译和生产构建。
- 桌面与窄屏视觉检查。
- 键盘焦点、溢出、空状态、错误状态和加载状态检查。

## 14. 测试策略

- 保留现有组件和页面测试，避免因结构调整丢失行为覆盖。
- 对新增通用组件先写失败测试，再实现。
- 关键页面测试继续验证路由、主要操作、状态和错误恢复。
- 生产构建必须成功。
- 视觉检查至少覆盖：运营总览、数据运行详情、审核工作台、定时任务、系统状态。
- 桌面和窄屏检查合并为最多两轮：第一轮发现问题，集中修复；第二轮确认。

## 15. 验收标准

- 全站使用统一的暖白、浅蓝、细描边圆角视觉语言。
- 不出现卡通人物、花草或云朵装饰。
- 总览页面舒展，数据与审核页面紧凑。
- 页面功能、API、路由、轮询、筛选、分页、审核和调度行为不变。
- 状态色、错误、空状态和加载反馈清晰。
- 桌面和窄屏无关键内容溢出或不可达操作。
- 键盘可以完成主要流程。
- 前端测试和生产构建通过。

## 16. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 只换色、结构仍旧 | 同时重构应用外壳、通用组件和关键页面布局 |
| 大留白降低数据效率 | 明确 `comfortable` 与 `compact` 两种密度 |
| CSS 继续膨胀 | 先建立令牌和组件规范，再写页面样式 |
| 页面改造破坏行为 | 测试先行，保留 API 与路由边界 |
| 多页面视觉不一致 | 分阶段改造后进行全站视觉验收 |
| 图标风格混乱 | 全站只使用一套线性图标规则 |
