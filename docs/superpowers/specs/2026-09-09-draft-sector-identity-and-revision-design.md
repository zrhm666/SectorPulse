# 草稿板块主体与真实修订设计

日期：2026-09-09。

状态：用户已确认设计，实施中。名称传递、内容主体检查和真实修订核心链路已实现；完整验收与历史数据修复尚未完成。执行状态见同日期实施计划。

## 1. 问题与已确认根因

用户看到章节使用“板块一、板块二”，正文直接以“该行业板块”开头，无法确认分析对象；正文还出现重复的“（已复核）”。

代码证据：

- `application/writing/attribution_gate.py` 的 `build_attribution_context` 从行情快照取涨跌幅、上涨广度和领涨股等字段，没有传递快照中的板块名称。
- `domain/writing/attribution.py` 的分析卡只有 `sector_id`、`sector_kind` 等字段，没有明确的板块名称契约；编排和写作主要消费这些分析卡。
- `config/prompts/writing.yaml` 当前只要求生成专业、清晰、非荐股草稿，没有要求章节主体可识别。
- `application/writing/phase1b_pipeline.py` 的自动修订循环没有调用修订模型，而是给被点名的章节追加“（已复核）”，递增版本并再次审核。
- 现有 `RewriteService` 没有接入上述自动修订循环；不能仅凭它存在就认为自动修订已实现。

因此 v2、v3 既可能来自人工编辑，也可能来自自动修订；版本增加本身不能证明文章确实得到修正。

## 2. 选择与边界

采用“可信名称贯穿链路、实际修订、校验后另存、针对新版本复审”。

其他方案及取舍：

1. 仅替换页面标签：改动小，但导出正文和模型输入仍缺主体，不能解决根因。
2. 只加强 prompt 并删除后缀：能减少表面问题，但审核仍没有真实修改能力，也缺少结果校验。
3. 本方案：补全数据契约和修订闭环，改动覆盖相关生成链路，但不重构全站或新增无关功能。

约束：

- 不根据章节顺序、新闻关键词或领涨股猜板块名称。
- 不伪造复核结果，不降低证据等级、引用和发布检查标准。
- 不覆盖旧版本，不继承旧版本的批准来发布新内容。
- 保持 SQLite/PostgreSQL 支持；优先利用已有 JSON 载荷、版本和审计结构，不新增数据库列。
- 不重新采集行情或新闻来修正文案；修订使用该运行已保存的事实与证据。
- 默认以 Fixture 和隔离数据库测试；真实 LLM 验证需另行说明次数与费用，不自动使用用户额度。
- 本轮不包含手动从全部行情板块自由选股、新闻全文抓取、前端视觉重构等功能。
- 当前会话执行，不使用子代理；合并和推送仍需单独指示。

## 3. 可信板块身份

### 3.1 数据契约

在 `AttributionContext` 和 `SectorAnalysisCard` 增加兼容旧数据的 `sector_name: str | None = None`。名称不是由模型发现或推断，而是来自同一次运行的行情快照。

流向：

```text
本次运行行情快照（类型、ID、名称）
  → AttributionContext.sector_name
  → 后端校准后的 SectorAnalysisCard.sector_name
  → 编排 / 写作 / 修订 / 审核输入
  → 章节标题与正文
```

- 实时采集写作桥接按 `(sector_kind, sector_id)` 匹配当前运行快照，将 `snapshot.name` 写入 context。
- 归因模型返回后，无论成功还是确定性降级，后端均用输入 context 中的名称设置分析卡；模型不能覆盖可信名称。
- 对已有运行的重试，优先读取保存的 context 名称；缺失时只能从该运行快照补齐。Fixture 则使用明确的测试名称映射。
- 历史 JSON 缺字段仍能读取。无法唯一映射时保留未知，不调用 LLM 猜测。
- 无法解析名称的章节使用可追溯的“行业板块〔ID〕”或“概念板块〔ID〕”作为降级主体，并记录名称缺失提示；不能使用“板块一”掩盖未知。提示放运行诊断，不写进文章正文。

### 3.2 写作规则

- 章节标题包含可信名称，例如“文化传媒：指数回落与个股普涨并存”；名称只是表达格式示例，不指认用户截图的实际板块。
- 正文第一句明确点名该板块；主体已经建立后，后文才可以使用“该板块”。
- `section.sector_id` 必须属于本次大纲，且章节与板块绑定唯一；重复、未知或错配 ID 不得直接保存为合格稿件。
- 标题、导语、正文、结论和风险提示均不得混入“（已复核）”“（已审核）”等已知工作流标记。
- 在写作输入中显式提供名称与 ID 映射，并在后端做确定性主体检查。仅调整 prompt 不作为验收完成标准。
- 首轮不合格但结构可解析的候选稿仍可保留为待修改版本，关联质量问题；不得标为已通过。利用真实修订流程修正；修订不可用时留待人工处理。

## 4. 真正的自动修订

### 4.1 触发与输入

触发条件为当前版本的自动审核决定 `REVISE`，或后端发现主体缺失、已知系统标记等确定性内容问题。后者转成可定位的审核问题，与模型审核结果一起处理；`BLOCK` 不通过自动修订绕过。

新增 `application/writing/revision_agent.py` 作为修订请求、候选验证与结果处理边界；管线负责调用、持久化和终态控制，不把全部逻辑继续堆进管线文件。

修订输入包含：当前草稿、受影响章节、审核问题与 suggested_fix、可信名称映射、板块分析卡、证据等级上限及允许引用的来源。新闻和文章均作为数据，不得将其中的命令当作系统指令。

复用配置中已有 `revision` 路由，新增明确版本号的 `config/prompts/revision.yaml`；遵循现有 prompt 限制 JSON 的兼容模式，不擅自增加供应商不支持的强制响应格式参数。

### 4.2 修订范围

- 定位到章节的问题：只允许修改对应 section 的 heading、body、claims 和 source_ids；保留 section_id、sector_id 和顺序。
- 定位到 claim 的问题：必须先归属到已有章节；未知 claim/section 标识不能静默忽略。
- 无章节定位的全局问题：允许修改标题、导语、结论、风险提示及受全局问题影响的章节，但仍使用显式修改集，不让模型替换整个草稿身份和来源目录。
- 修订输出使用专门的结构化修改集，禁止修改 draft_id、run_id、version、status、原始行情、证据和可信名称。
- 未涉及的字段原样保留；整批修改通过校验后才应用，任何一项不合法都不保存部分修改。

### 4.3 候选验证

校验包括：输出结构正确；目标字段合法且无重复；章节身份不变；主体明确；无已知系统标记；引用仅来自本次验证过的来源；claim 的证据引用可解析且不越过原证据上限；没有已禁止的荐股表达。

允许删去未经证实的 claim，不允许用旧 claims 描述已经被改写成另一层意思的正文。语义真实性不能只靠 ID 和字符串验证，修改后的版本仍必须重新审核。

没有任何实际内容变化视为 `REVISION_NO_CHANGE`，不制造 v2。格式错误、身份错配、越界引用、超时等产生安全诊断，不把供应商原始报错写进文章。

### 4.4 版本与状态

| 情况 | 保存与结果 |
| --- | --- |
| 首次结构有效草稿 | v1，尚未人工批准 |
| 一次修订成功且内容有变化 | 原 draft_id 下另存 v(n+1)，未修改字段不变 |
| 修订请求失败或校验不通过 | 保留最后有效版本，不递增版本；待修改，记录失败原因 |
| 新版本自动审核不可用 | 保留新版本，标为未审核；旧版本 PASS 不能用于它 |
| 新版本自动审核 PASS 且确定性检查通过 | 可进入人工审核，不等同于人工批准 |
| 新版本 REVISE 且轮次耗尽 | 保留最新有效版本，提示仍需修改 |
| BLOCK | 保持阻断及审核问题，不因生成新版本消除限制 |

审核结果必须校验 `draft_id` 和 `draft_version` 对应当前版本，拒绝错配报告。沿用最多两轮修订上限；每轮指一次实际修订尝试，不因失败、无变化或断线无限重试。

修订请求纳入已有 invocation 的模型、耗时、状态、token 和成本记录。调用前检查剩余预算，计费结果回来后更新总成本并重新判断预算；预算不足时保留现有产物，不继续下一次请求。

新增 `revision.started / revision.done / revision.failed` 等进度事件只携带必要状态、版本和安全原因；不把状态文字拼入正文。应检查现有事件消费者兼容未知事件，避免修订事件破坏已有阶段显示。

## 5. 已有草稿的安全修复

不做启动时批量清理，也不直接 UPDATE 所有历史正文。

1. 提供按明确 `run_id`、`draft_id` 和预期最新版本运行的修复工具，默认 dry-run。
2. 从该运行快照按章节的板块 ID 和类型解析真实名称；禁止按“第一章对应第一个候选”匹配。
3. 对可确认的“板块一/二”等泛称标题补明确主体；首句只有指代时补真实名称。仅清除已确认由系统追加、位于章节尾部的重复标记，不全局删除正常引用中的“已复核”字样。
4. 输出修复前后差异、目标版本、无法定位的主体及将被修改的字段，不写库、不调用 LLM。
5. 用户确认具体预览后，才执行 apply；在事务中复核当前版本，另存一个待审核的新版本并记录修复来源。版本冲突拒绝写入，不覆盖并发人工修改。
6. 原版本、原审核和原批准均保留，但不使修复后新版本自动获得旧批准；导出必须仍校验当前版本审批。

名称无法恢复的历史稿件报告缺失项，不猜测、不整篇重新生成。已有通用 patch 保存路径的版本检查与审计若不能保证本次修复原子性，需要在实现中补齐双方言事务测试后才能使用，不能用“先存版本、后存审计”的两次独立提交冒充原子修复。

本设计批准不等同于批准修改任意业务草稿；实际应用历史修复需单独确认目标和差异。

## 6. 影响范围与兼容

- 领域契约：`domain/writing/attribution.py`。
- 名称构建：`application/writing/attribution_gate.py`、`attribution_agents.py`、`application/data_runs/real_data_writing_bridge.py` 及重试输入恢复路径。
- 生成与修订：`editorial_agents.py`、新增 `revision_agent.py`、`phase1b_pipeline.py`；不强行复用缺少完整审核上下文的旧 RewriteService。
- 提示词与路由：writing/editorial/review 的主体要求、revision 新提示词、现有模型路由与调用成本记录。
- 历史修复：独立 dry-run/apply 工具和所需版本/审计原子操作，支持 SQLite/PostgreSQL。
- 前端：仅在必要时补修订阶段/失败说明，沿用现有状态组件；正文中的来源、版次和审核状态分离，不做页面样式重构。

新增名称字段有默认值，以兼容旧数据与 Fixture；JSON 中的追加字段不需要重采集或全库迁移。若实现发现必须改表，先更新设计和迁移方案，不直接动业务库。

## 7. 实施阶段与验收

### 阶段一：板块身份与内容约束

先写失败测试，再补名称传递、模型输出校准及写作约束。验收：标题/首句能识别主体，模型不能伪造名称，旧 JSON 可读，缺名称时可追溯且不猜测；涵盖行业/概念、相似名称及未知 ID。

### 阶段二：实际修订闭环

用可控 Fixture 返回真正不同的修订文字，验证审核问题确实进入模型输入、只修改允许字段、版本只在成功变化后增加。覆盖无变化、非法来源、错配审核、超时、预算不足、两轮上限和新版本复审失败。删除追加标记的旧逻辑及依赖假修订的测试假设。

### 阶段三：历史草稿修复预览

测试 dry-run 零写入；apply 保留历史、原子保存新版本和审计；并发版本冲突拒绝写入；重复执行不再新增无意义版本；不能移植旧批准。先用隔离 SQLite 和 PostgreSQL 测试，业务草稿仅做经用户允许的预览。

### 阶段四：集成验收与交付

- 后端非 Live 全量测试、Ruff、严格类型检查及 Fixture 真实 HTTP 生成/审核/导出流程。
- SQLite/PostgreSQL 的版本、JSON 兼容和事务测试；缺隔离 PostgreSQL 条件时明确标为未验证。
- 若前端受影响，运行前端测试、构建和桌面/窄屏状态验证。
- 文档说明 v1/v2 是内容快照，不是审核次数或通过次数；修订与审核成本分别记录。
- 验收记录区分代码修复、历史预览、历史实际写入以及真实 LLM 验证；不能以 Fixture 通过冒充真实模型效果。

## 8. 自检结论

名称有可信来源；未知主体有显式处理；修订确实调用模型且有限次；正文不承载系统状态；版本、审核与批准严格绑定；历史修复需预览且不覆盖原稿。没有要求重新采集、默许真实 LLM 费用或批量修改业务数据。
