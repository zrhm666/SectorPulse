# Phase 1A.2 真实新闻接入与映射验收设计

## 1. 阶段定位

Phase 1A 已完成行情快照、新闻事件、候选板块和证据包的 fixture 垂直切片，但尚未完成真实新闻来源的网络验收。Phase 1A.2 在进入 LLM 归因与文案生成之前，补齐真实新闻 Provider、受控检索、板块实体映射、来源质量门禁和盘中/盘后验收。

本阶段只回答三个问题：

1. 系统能否在 5 分钟内稳定获得与 A 股行业、概念板块相关的真实新闻；
2. 系统能否把新闻谨慎地关联到板块，并保留可核验的映射理由；
3. 系统能否明确区分无数据、部分失败、整体失败和数据过期。

新闻与板块存在关联不等于新闻造成了板块涨跌。本阶段不调用 LLM、不生成文案，也不产生“明确驱动”或“可能催化”结论。真实新闻验收通过后，才进入 Phase 1B 的归因与成文设计。

## 2. 目标与非目标

### 2.1 目标

- 默认接入财联社全局快讯、东方财富关键词新闻和巨潮资讯公告；
- 对 A 股全部行业和概念板块完成市场扫描，再对有限预候选执行新闻检索；
- 通过全局快讯补回未进入市场预候选但存在突发事件的板块；
- 使用股票代码、板块成分关系、规范别名和产业链词完成确定性实体映射；
- 保存来源执行、查询计划、新闻事件、板块关联和质量判定；
- 输出盘中和盘后互不覆盖的真实数据验收报告；
- 保持 Provider 可替换，RSSHub、RSS 和 Tushare 以后可作为插件接入。

### 2.2 非目标

- 不调用任何大模型；
- 不判断新闻是否造成板块涨跌；
- 不生成 `Claim`、`SectorBrief` 或社区稿；
- 不实现 FastAPI、Web 管理台、调度器或自动发布；
- 不对约 1000 个板块逐一调用新闻搜索；
- 不把公开网页接口视为长期正式授权数据源。

## 3. 来源组合与使用边界

### 3.1 财联社全局快讯

通过 AKShare 的财联社电报接口获取全局快讯。该接口返回标题、内容、发布日期和发布时间，但当前不提供逐条原文链接，因此定位为 `DISCOVERY_ONLY`：

- 可用于发现政策、产业和突发主题；
- 可触发非市场预候选板块的补召回；
- 不能单独成为正文引用来源；
- 不能单独支持因果归因。

### 3.2 东方财富关键词新闻

通过 AKShare 的东方财富个股/关键词新闻接口，使用板块规范名、受控别名、产业链词和代表性成分股进行检索。结果包含标题、摘要、发布时间、文章来源和链接：

- 作为候选证据的主要发现来源；
- 来源等级依据原始文章来源确定，不能因聚合页面来自东方财富而统一升级；
- 缺少链接或发布时间的条目只能降级使用；
- 查询次数必须受运行预算限制。

### 3.3 巨潮资讯公告

通过 AKShare 的巨潮资讯公告接口，按重点公司和时间窗查询公告：

- 公告属于一手来源，可标记为 `PRIMARY`；
- 只查询预候选板块的核心成分股和全局突发映射出的重点公司；
- 公告存在只证明公司披露了事件，不证明事件驱动板块涨跌。

### 3.4 备用来源

- 现有 `RssNewsAdapter` 保留，作为可选插件，不承担默认核心来源；
- RSSHub 仅预留 Provider 注册位，不依赖公共实例完成本阶段验收；
- Tushare 仅预留 Token Provider 接口，不要求用户在本阶段购买新闻权限。

所有默认来源继续标记为 `RESEARCH_ONLY`。若用于长期商业化运行，必须重新审查数据授权和站点条款。

## 4. 总体数据流

采用“双通道、两阶段召回”。

### 4.1 第一阶段：市场预候选

1. 运行 Phase 0 行业、概念行情采集和质量检查；
2. 锁定 `run_cutoff_at`，锁定后不得向前移动；
3. 行业和概念分别标准化涨跌、成交活跃度和涨跌家数扩散；
4. 在不使用新闻分数的情况下生成 20～30 个市场预候选。

该阶段避免“因为已有新闻才搜索新闻”的循环依赖。

### 4.2 第二阶段：新闻双通道召回

通道 A 是候选定向检索：

1. 为市场预候选生成规范关键词；
2. 默认最多执行 24 次东方财富关键词查询；
3. 默认最多对 12 个核心股票代码执行巨潮公告查询。

通道 B 是全局突发发现：

1. 每轮只调用一次财联社全局快讯；
2. 对快讯执行实体映射；
3. 高置信映射到非市场预候选板块时，将板块补入候选池；
4. 补召回只改变候选资格，不提升归因等级。

### 4.3 最终候选

新闻去重、时间门禁和实体映射完成后，重新计算新闻丰富度，并在行业、概念各自标准化后合并排序，输出 8～12 个最终候选。新闻丰富度使用去重事件数、时效和来源质量，不使用转载篇数直接累加。

## 5. 组件与接口边界

### 5.1 `NewsSourceCatalog`

负责读取和校验来源配置，输出不可变的来源定义。来源定义至少包含：

- `source_id`；
- `provider_type`；
- `enabled`；
- `authorization_status`；
- `default_source_grade`；
- `timeout_seconds`；
- `max_retries`；
- `rate_limit_per_second`；
- `max_results_per_query`。

配置只能引用代码中注册的 `provider_type`，不能通过 YAML 动态导入任意 Python 类。

### 5.2 新闻 Ports

拆分三个能力 Port：

- `GlobalNewsDiscoveryPort.fetch_global(cutoff)`：获取全局快讯；
- `KeywordNewsSearchPort.search(query, start_at, cutoff)`：按关键词和时间窗检索新闻；
- `DisclosureSearchPort.search_disclosures(stock_codes, start_at, cutoff)`：查询公司公告。

每个 Port 返回 `ProviderResult`，继续使用 `SUCCESS`、`EMPTY`、`PARTIAL`、`FAILED`、`STALE` 和 `UNAVAILABLE` 的明确语义。领域层不得接触 Pandas `DataFrame` 或供应商原始响应。

### 5.3 `NewsRetrievalPlanner`

输入市场预候选、板块实体词典、成分股关系和运行预算，输出不可变的 `NewsQueryPlan`。计划包含查询类型、关键词或股票代码、关联板块、优先级、来源和预算消耗。

规划规则是确定性的，同一输入和规则版本必须生成相同计划。默认预算为：

- 财联社全局查询 1 次；
- 东方财富关键词查询最多 24 次；
- 巨潮公告股票代码最多 12 个；
- 单个 Provider 并发上限 4；
- 单个请求失败最多重试 2 次。

### 5.4 `SectorEntityResolver`

输入 `NewsEvent`、板块实体配置和本轮成分股关系，输出零个或多个 `SectorEventLink`。映射依据按可靠性排序：

1. 新闻中的股票代码或唯一公司实体，经成分股关系映射到板块；
2. 板块规范名精确命中；
3. 经审核的唯一别名命中；
4. 产业链词与其他上下文词组合命中。

歧义词不得单独产生高置信映射。无法可靠区分的实体必须拒绝映射。

`SectorEventLink` 至少包含：

- `run_id`；
- `event_id`；
- `sector_id` 和 `sector_kind`；
- `relation_type`；
- `matched_entities`；
- `mapping_confidence`，取 `HIGH`、`MEDIUM` 或 `LOW`；
- `mapping_reason`；
- `rule_version`。

`mapping_confidence` 是规则映射可靠度，不是新闻因果概率。

### 5.5 `NewsQualityGate`

负责：

- 排除 `published_at` 或 `observed_at` 晚于 `run_cutoff_at` 的数据；
- 将缺少 `published_at` 的新闻限制为背景；
- 检查可核验 URL、来源 ID 和内容哈希；
- 合并转载或改写事件；
- 汇总每个来源及每个查询的状态；
- 阻止来源失败被解释为“没有新闻”。

### 5.6 候选与证据包修正

现有实现只要新闻事件关联到板块，就将 `EvidencePack.max_level` 设为 `POSSIBLE_CATALYST`，该行为必须修正：

- 确定性实体映射最多允许 `MARKET_ASSOCIATION`；
- 没有可靠映射时为 `NO_RELIABLE_EXPLANATION`；
- `POSSIBLE_CATALYST` 和 `EXPLICIT_DRIVER` 只能由后续 Phase 1B 在检查来源、时序、板块特异性、市场印证和替代解释后产生。

## 6. 配置设计

### 6.1 `config/news_sources.yaml`

保存来源运行参数和授权状态。密钥只允许通过环境变量引用，不允许写入 YAML、SQLite、报告或日志。本阶段默认 Provider 不需要 API Key。

### 6.2 `config/sector_entities.yaml`

保存：

- 板块规范名；
- 经审核的别名；
- 产业链关键词组合；
- 禁止单独匹配的歧义词；
- 规则版本。

股票代码和板块成分关系由行情 Provider 获取并随运行版本保存，不在 YAML 中长期复制。

## 7. 持久化设计

新增 SQLite `002` 迁移，至少包括：

### 7.1 `news_source_runs`

保存每个来源在一次运行中的开始时间、结束时间、调用数、重试数、状态、延迟和安全错误码。

### 7.2 `news_queries`

保存规范化查询摘要、查询类型、来源、优先级、关联板块、时间窗、状态和返回数量。不得保存密钥、Cookie 或完整请求头。

### 7.3 `sector_event_links`

保存事件与板块的关联、映射类型、命中实体、可靠度、理由和规则版本。唯一键至少包含 `run_id`、`event_id`、`sector_id` 和 `sector_kind`。

### 7.4 现有表扩展

`news_documents` 补充文章来源、可选摘要、使用等级和字段质量标记。摘要必须限制长度；本阶段不持久化完整受版权保护的新闻正文。

盘中和盘后运行使用不同 `run_id`，后一次运行不得覆盖前一次数据。

## 8. 状态、降级与错误处理

- `EMPTY`：请求成功，但指定时间窗内没有数据；
- `PARTIAL`：部分查询失败或部分字段不可用，成功数据仍可追溯使用；
- `FAILED`：Provider 整体请求失败，或所有必要查询均失败；
- `STALE`：仅获得超过允许时间窗的数据；
- `UNAVAILABLE`：能力未配置、被禁用或当前运行模式不支持。

降级规则：

- 财联社失败时，可以使用市场预候选加东方财富和巨潮继续运行，但记录全局突发发现缺失；
- 东方财富失败时，可以保留财联社发现和巨潮公告，但不得把财联社无链接内容当成可引用证据；
- 巨潮失败时，媒体新闻仍可用于候选关联，但一手公告能力标记为缺失；
- 东方财富和巨潮同时失败时，本轮不得进入 Phase 1B 归因；
- 核心行情质量被阻断时，不执行真实新闻检索；
- 所有异常对外只暴露安全错误码，敏感请求信息不进入普通日志。

## 9. 安全与合规边界

- 默认来源固定为注册 Provider，不允许用户配置任意抓取脚本；
- 现有 RSS 安全客户端继续拒绝非 HTTP(S)、内网地址、危险重定向和超大响应；
- 新闻文本始终作为不可信数据处理，清理 HTML、脚本和控制字符；
- 新闻中的指令性文字不得改变查询计划或运行配置；
- 数据报告只保存短摘要、结构化元数据和哈希，不复制完整文章；
- 来源链接和媒体名称必须由 Provider 映射产生，后续模型不得生成或修补 URL；
- 当前公开接口只用于研究验证，正式生产使用前重新审查授权。

## 10. 测试设计

### 10.1 领域单元测试

覆盖：

- cutoff 之后的新闻被排除；
- 缺发布时间的新闻只能作为背景；
- `FAILED`、`EMPTY`、`PARTIAL` 和 `STALE` 不混淆；
- 股票代码和唯一别名产生可解释映射；
- 歧义词不会单独产生高置信映射；
- 新闻关联不会自动升级为 `POSSIBLE_CATALYST`。

### 10.2 Provider 契约测试

使用固定响应 fixture 分别验证：

- 财联社日期与时间合并为 UTC 时间；
- 东方财富标题、摘要、文章来源、发布时间和 URL 映射；
- 巨潮公告股票代码、标题、公告时间和链接映射；
- 空响应、字段变化、网络异常和部分无效行的状态语义。

### 10.3 集成测试

覆盖：

- 两阶段查询计划遵守调用预算；
- 三个 Provider 的成功和失败结果可共同汇总；
- 新闻去重后建立 `SectorEventLink`；
- SQLite `002` 迁移幂等；
- 同一天的盘中和盘后运行互不覆盖；
- 验收报告不包含密钥、Cookie、完整正文或内部异常栈。

### 10.4 Live 测试

真实网络测试必须显式提供 `.live-data-consent`；默认测试套件不访问网络。Live 测试逐来源运行，并将失败保留为真实失败，不使用 fixture 伪装成功。

## 11. 真实验收标准

Phase 1A.2 只有同时满足以下条件才算通过：

1. 默认运行总时长不超过 5 分钟；
2. 100% 排除 cutoff 之后的新闻和公告；
3. 缺失发布时间的新闻全部限制为背景；
4. 所有候选证据有来源 ID，用于引用的证据有可核验 URL；
5. 标注 fixture 中的高置信板块映射准确率不低于 90%；
6. 完成一次盘中真实运行和一次盘后真实运行；
7. 两次运行分别保存报告和数据库记录，不互相覆盖；
8. 报告包含各来源调用数、成功率、延迟、文档数、去重率、映射率和降级原因；
9. 东方财富与巨潮不能同时处于 `FAILED` 或 `UNAVAILABLE`；
10. Ruff、mypy、默认非 live 测试和显式 live 验证结果分别记录。

网络或上游接口不稳定导致 live 验收失败时，保留失败报告并修复 Provider；不得降低状态门禁来获得通过结果。

## 12. CLI 与交付物

新增独立 CLI 命令执行 Phase 1A.2，不改变现有 `phase0-probe` 和 `phase1a-probe` 的行为。命令支持：

- 指定运行类型为盘中或盘后；
- 指定来源配置和实体配置；
- 指定数据库和报告输出目录；
- 显式 live consent；
- 输出安全的阶段进度和最终状态。

交付物包括：

- 三个默认真实新闻 Provider；
- 来源目录、查询规划器、实体映射器和质量门禁；
- SQLite `002` 迁移及 Repository；
- 领域、契约、集成和 gated live 测试；
- 盘中和盘后真实验收报告；
- Provider 矩阵更新。

所有关键类、边界转换、状态降级和异常分支使用中文注释。代码继续遵循 Ports & Adapters，Infrastructure 只实现 Port，运行时由依赖注入装配。

## 13. 后续阶段入口

Phase 1A.2 通过并经用户审核后，Phase 1B 才设计和实现：

- `LLMProviderPort` 与可替换 OpenAI 兼容 Provider；
- `Claim + Fact IDs + Evidence IDs + AttributionLevel`；
- Evidence Analyst、Selection Editor、Community Writer 和 Reviewer；
- 3～6 个重点板块和一篇 1000～1800 字通用稿；
- 确定性来源清单、Prompt 版本、成本和人工修改记录。
