# SectorPulse 高保真前端重构设计

> 日期：2026-08-27
> 状态：已逐节确认
> 分支：`refactoring`
> 项目规范：[SectorPulse 高保真运营后台 UI 规范](../../design/sectorpulse-reference-ui-system.md)
> 取代范围：本设计在后续重构阶段取代 [2026-08-26 柔和蓝白重构设计](./2026-08-26-sectorpulse-soft-blue-ui-redesign-design.md) 的页面布局与实施策略；原文仍保留为上一轮实现记录。

## 1. 背景

SectorPulse 已具备运营总览、分析运行、数据运行、候选板块选择、内容生成、审核治理、定时任务、系统状态和影子验收等真实业务页面。上一轮前端重构已经建立浅色蓝白基础风格，但实际页面仍与 README 中的三张设计参考图存在明显差距：信息架构偏简单、布局比例不够稳定、工作台内容较长、审核页面左右权重不平衡，并且 README 容易让人误以为参考图就是当前产品截图。

本轮从 `main` 创建 `refactoring` 分支，以三张参考图作为高保真视觉与布局目标，对前端进行设计系统驱动的渐进式重构；必要时增量调整后端接口和数据库，但不制造无关功能、假按钮或假数据。

## 2. 已确认决策

1. 参考图是高保真视觉和布局目标，不是逐项功能清单。
2. 只展示真实存在或确有业务价值的能力；无关或实现效果差的功能不强行加入。
3. 全站只使用一套统一侧边栏，菜单继续采用 SectorPulse 真实页面。
4. 先建立项目专用 UI 规范，作为所有阶段的唯一视觉基准。
5. 桌面端在 1536×1024 和 1440×900 下进行高保真验收。
6. 平板和移动端使用专门的响应式重排，保证完整功能，不压缩桌面布局。
7. 审核稿继续使用结构化字段和证据锚点，视觉上改造成连续文档编辑。
8. 使用设计系统驱动的渐进式重构，不采用一次性 `web-v2` 大爆炸重写，也不按页面复制一次性 CSS。
9. 当前会话按阶段连续执行；只有必要外部条件或重大需求冲突才暂停。

## 3. 目标

- 让真实产品在层级、比例、密度和视觉气质上高保真接近三张参考图。
- 建立可维护的设计令牌、应用外壳、通用组件和页面模式。
- 解决当前侧边栏与内容共同滚动、长页面信息堆叠和审核页面失衡问题。
- 保留现有路由、工作流、轮询、候选板块选择、草稿版本、证据和治理能力。
- 让 Dashboard、数据工作台和审核工作台分别适配其任务密度。
- 对新页面需求提供真实、可追溯的后端数据。
- 完成桌面、平板和移动端验收，并以实际页面替换 README 参考图展示。

## 4. 非目标

- 不为视觉相似度添加用户权限、通知中心、数据源管理等无关模块。
- 不用静态数字、模拟曲线或假状态填充正式页面。
- 不重写数据采集、归因、写作、审核和治理的核心业务逻辑。
- 不立即引入任意 WYSIWYG 富文本编辑器。
- 不改变现有 URL。
- 不引入 Tailwind、大型 UI 框架或仅为一张图使用的重型依赖。
- 不在本轮直接合并 `main`；完成后先在 `refactoring` 验收。

## 5. 选择的重构策略

采用“设计系统驱动的渐进式重构”：

1. 先冻结 UI 规范、页面结构和接口约束。
2. 重构应用外壳和基础组件。
3. 依次迁移运营总览、数据工作台、审核工作台和剩余页面。
4. 每个阶段保持路由和业务可运行，独立测试、浏览器验收和提交。
5. 新后端字段使用增量迁移和兼容响应。

未采用方案：

- 平行建设 `web-v2`：长期双维护、合并和回归风险过高。
- 按截图逐页重画：容易产生一次性 CSS，无法维持全站一致性。

## 6. 参考图提炼

### 6.1 共同视觉特征

- 固定白色侧边栏和细分隔线。
- 浅蓝灰主背景、白色面板、清透蓝主色。
- 16px 左右圆角、轻边框、弱阴影。
- 大标题、短说明、右侧主操作组成清晰页首。
- 使用线性图标、紧凑状态标签和轻量表格。
- 总览页面留白较多，数据与审核工作区密度更高。

### 6.2 必须适配而非照搬的内容

- 参考图中的用户、权限、告警、数据源管理等不直接转化为功能。
- 参考图中的数字和趋势不作为正式数据。
- 参考图中的顶部通知和账户区域不实现，除非未来引入真实账户体系。
- 参考图中的富文本工具栏不直接加入审核工作台。

## 7. 全站信息架构

### 7.1 统一导航

```text
运营
├─ 运营总览          /
├─ 分析运行          /runs
└─ 审核工作台        /review

管理
├─ 定时任务          /schedules
├─ 系统状态          /system
└─ 影子验收          /shadow-acceptance
```

`/runs/new` 通过“新建分析”进入；`/data-runs/:runId`、`/runs/:runId` 和 `/task-runs/:runId` 是上下文二级页面。

### 7.2 应用外壳

- 桌面侧边栏约 224–236px，固定不随内容滚动。
- 顶部栏约 64–68px，显示页面上下文和真实系统就绪状态。
- 主内容区独立滚动。
- Dashboard 使用限制宽度；Workbench 使用更宽内容区；Review Workspace 使用可用全宽。
- 低频入口通过导航分组降低竞争，不删除功能。

### 7.3 响应式

- `>=1280px`：完整侧边栏。
- `1024–1279px`：缩窄侧边栏和页面安全间距。
- `<1024px`：侧边栏转抽屉。
- 审核工作台在窄屏转为队列、草稿、证据三个页签。
- 数据表格按任务保留关键列，其余进入详情。

## 8. 前端架构

### 8.1 样式组织

```text
web/src/styles/
├─ tokens.css
├─ base.css
├─ shell.css
├─ components/
├─ patterns/
├─ pages/
└─ responsive.css
```

使用 CSS cascade layers 管理覆盖顺序。现有单一 `styles.css` 按阶段拆分，迁移期间允许兼容入口，但新样式不得继续无结构堆积。

### 8.2 组件边界

跨页面组件：

- AppShell、Sidebar、Topbar、PageHeader
- MetricCard、Panel、StatusBadge、InlineAlert
- DataTable、Pagination、FilterBar、Tabs、Stepper
- Drawer、ConfirmDialog、LoadingState、EmptyState、ErrorState

业务模块组件：

- 候选板块选择器和数据运行阶段面板
- 连续结构化草稿编辑器
- 证据来源与治理决策面板

不为形式上的复用把业务复杂组件拆成难以理解的通用抽象。

### 8.3 数据访问层

```text
web/src/api/
├─ client
├─ operations
├─ runs
├─ dataRuns
├─ review
├─ schedules
└─ system
```

每个模块负责请求、响应类型、页面模型转换和标准错误解析。页面组件不得散落直接 `fetch`。

## 9. 运营总览设计

### 9.1 布局

```text
页面标题 + 操作区
├─ 核心指标卡（4 张）
├─ 运行趋势（约 2/3）+ 系统就绪状态（约 1/3）
└─ 最近运行记录
```

适配原型：[operations-dashboard-layout.html](../../design/prototypes/operations-dashboard-layout.html)

### 9.2 指标

- 运行总数
- 今日已完成
- 运行中
- 异常与待处理

指标变化仅在能够从数据库可靠计算时显示。无法计算时返回 `null` 和原因。

### 9.3 趋势与状态

- 趋势支持最近 7 天和 30 天。
- 显示总运行、成功和失败。
- 系统状态包含 PostgreSQL、实时数据 Provider、LLM 和调度器。
- 状态项可以进入系统状态详情。

### 9.4 最近运行

表格展示运行、场景、状态、Provider、候选板块、创建时间、耗时和操作，默认 8–10 条。

### 9.5 刷新

存在运行中任务时每 5 秒刷新摘要；页面隐藏时暂停；失败时保留最后成功数据并提示过期。

## 10. 数据运行工作台设计

### 10.1 页面结构

```text
运行标题与状态
├─ 运行摘要条
├─ 行情采集 / 预候选排序 / 新闻采集 / 证据构建 / 归因就绪
├─ 本次数据获取概览与来源状态
├─ 候选板块选择
└─ 行情 / 新闻 / 证据 / 质量页签
```

### 10.2 候选板块选择

- 默认选择综合评分靠前板块。
- 支持搜索、排序、全选和取消选择。
- 展示板块名称、代码、类型、涨跌、热度、新闻覆盖和综合评分。
- 选择结果持久化到 PostgreSQL。
- 未确认选择前禁用草稿生成。
- 刷新后保留选择、筛选和页面上下文。

### 10.3 数据详情

- 行情、新闻、证据和质量使用独立页签。
- 新闻明确区分正文、摘要和快讯。
- 有真实 URL 时才显示原文入口。
- 大列表服务端分页、排序和筛选。
- 行详情和新闻详情使用抽屉。

### 10.4 长流程处理

- 只展开当前阶段，已完成阶段可折叠。
- 页面使用一个主滚动区。
- 主要操作可固定在底部吸附栏。
- 运行中每 2 秒轮询，终态停止，页面隐藏时暂停或降频。

## 11. 审核工作台设计

### 11.1 桌面比例

```text
审核队列 22% | 草稿编辑区 53% | 证据与决策 25%
```

- 左栏最小约 260px。
- 中栏有效正文宽度约 680–820px。
- 右栏约 320–380px。
- 三栏顶部对齐，各自按任务独立滚动。

### 11.2 审核队列

展示标题、运行场景、版本、候选板块数量、创建时间、治理状态和待处理证据，并支持状态筛选。

### 11.3 连续结构化编辑

- 保留标题、导语、分节正文、结论和风险提示。
- 输入边界在聚焦时强调，非聚焦时形成连续文档观感。
- 停止输入和失焦时自动保存。
- 显示未保存、保存中、已保存、失败和冲突。
- 历史版本只读比较；恢复旧版本需要创建新版本。

### 11.4 证据和治理

右栏分来源、证据判定和治理记录。来源随当前段落变化；证据支持保留、降权、排除和理由。保存决策不会无提示改写正文。

### 11.5 审核操作

批准、退回和撤销批准按后端状态显示。批准前检查未保存内容、必要字段、治理状态和关键证据。

## 12. 其余页面

### 12.1 分析运行列表

使用筛选工具条和紧凑表格，支持状态、场景、Provider 和时间范围筛选；失败记录可展开错误与重试信息。

### 12.2 新建分析

按场景、Provider 与时间、确认参数、启动分析四步组织。高级参数默认折叠，提交前说明数据源和模型。

### 12.3 内容运行详情

按归因、编辑、写作、审核和治理显示阶段。失败时展示阶段、错误、重试次数和快照恢复能力；成功后进入审核工作台。

### 12.4 定时任务

使用列表和编辑抽屉，展示计划、状态、最近执行和下次执行。删除需要确认。

### 12.5 系统状态

展示数据库、Provider、LLM、调度器、版本和许可状态，包括检查时间、耗时、可读错误和处理建议，不暴露敏感配置。

### 12.6 影子验收

展示验收周期、进度、样本、通过率、阻断项和报告能力；当前未运行时显示真实空状态。

## 13. 后端与数据契约

### 13.1 兼容策略

- 保留现有 API 路径和已有响应字段。
- 新字段使用增量扩展。
- 新数据库结构使用可回滚迁移。
- 旧数据无法补全的字段保持未知，不伪造默认值。

### 13.2 统一运行状态

```text
queued
running
waiting_for_selection
waiting_for_draft
waiting_for_review
completed
failed
cancelled
```

运行响应还应提供当前阶段、完成阶段、可执行操作、错误类型、可读信息、重试能力、快照能力和更新时间。

### 13.3 运营摘要

聚合响应包含：

```text
summary
trend
readiness
recent_runs
generated_at
```

### 13.4 数据运行视图

页面模型包含：

```text
run_summary
workflow_stages
acquisition_summary
provider_statuses
candidates
market_records
news_records
evidence_records
quality_report
selection
```

### 13.5 候选选择记录

保存运行 ID、已选板块、默认/人工方式、操作时间、数据版本和修改次数。草稿生成读取已确认版本。

### 13.6 审核并发

保存草稿携带版本号。版本冲突时后端拒绝静默覆盖，前端提供比较与重新应用。

## 14. 轮询和错误处理

- 数据运行：2 秒。
- 内容运行：2 秒。
- 运营总览：存在运行任务时 5 秒。
- 系统状态：手动或低频刷新。
- 页面隐藏时暂停或降频。
- 前一次请求未结束时不发起重复请求。
- 终态自动停止。
- 连续失败指数退避并提供手动恢复。
- 错误页面保留最后一次成功数据和更新时间。

## 15. 数据库迁移原则

- 所有迁移增量、可回滚。
- 新字段允许空值或提供可靠默认值。
- 先完成迁移和兼容读取，再启用新写入。
- 不删除现有运行、草稿、新闻、证据和审核记录。
- 迁移前后执行完整性检查。

## 16. 安全与审计

- API Key、数据库密码只存在于后端环境变量。
- 前端只显示是否配置和是否可用。
- 原始堆栈写后端日志，前端显示安全可读错误。
- 外部新闻链接校验协议和来源。
- 草稿修改、证据判定、批准、撤销和退回保留审计记录。

## 17. 实施阶段

### Phase 0：规范与架构冻结

完成项目 UI 规范、本设计、页面/API 审计和总实施计划。本阶段不修改业务代码。

### Phase 1：应用外壳与基础组件

完成统一侧边栏、顶部栏、内容滚动、设计令牌、CSS 分层、基础组件和响应式框架。

### Phase 2：运营总览

完成指标、趋势、系统状态、近期运行和所需聚合 API。

### Phase 3：数据运行工作台

完成运行摘要、阶段、来源、候选选择、数据页签、详情抽屉、持久化和轮询。

### Phase 4：审核工作台

完成三栏布局、连续结构化编辑、自动保存、版本冲突、来源证据和审核操作。

### Phase 5：其余页面

完成运行列表、新建分析、内容运行、定时任务、系统状态、影子验收和通用页面状态。

### Phase 6：全项目验收

完成自动化测试、生产构建、浏览器视觉验收、响应式、无障碍、性能、最终代码审查、README 实际截图和文档更新。

## 18. 每阶段工作方式

```text
阶段设计
→ 阶段实施计划
→ 测试先行
→ 前后端实现
→ 浏览器视觉验收
→ 自动化测试
→ 阶段提交
→ 下一阶段
```

实施阶段使用：

- `image-to-code`：提取并对照参考图布局。
- `design-taste-frontend`：控制设计质量和一致性。
- `impeccable`：审核信息架构、响应式、无障碍和细节。
- `test-driven-development`：行为测试先行。
- `systematic-debugging`：出现异常时定位根因。
- `verification-before-completion`：提交前验证。
- `requesting-code-review`：阶段和最终审查。

### 19.3 关键路径

## 20. 验收标准

- 实际页面在层级、比例、密度和视觉气质上高保真接近三张参考图。
- 全站只有一套统一导航和应用外壳。
- 侧边栏固定，主内容独立滚动。
- 所有指标、趋势、状态、来源和按钮都绑定真实能力。
- 运营总览、数据工作台和审核工作台分别使用适合任务的页面模板。
- 候选选择、草稿版本、证据和治理记录在刷新和重试后保持一致。
- 现有路由和关键工作流无回归。
- 桌面高保真、窄屏功能完整。
- 自动化测试、构建、迁移和浏览器验收通过。
- README 最终使用真实产品截图，不再把设计参考图当成产品现状。

## 21. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 重构范围大导致长期不可用 | 渐进迁移，每阶段保持可运行并独立提交 |
| 只换皮不改布局 | 先冻结三类页面模板和信息架构 |
| 为接近参考图制造假功能 | 使用真实性规则和接口追溯验收 |
| CSS 再次膨胀 | 令牌、层级、组件、模式和页面样式分层 |
| 后端接口被前端绑死 | 使用兼容扩展和页面模型转换层 |
| 旧数据无法满足新指标 | 返回未知和原因，不伪造零值 |
| 审核编辑破坏证据锚点 | 保留结构化字段、版本和哈希 |
| 多栏工作区窄屏不可用 | 使用专门页签模式，不压缩三栏 |
| 数据库迁移损坏历史记录 | 增量迁移、完整性检查、阶段提交和回滚点 |

## 22. 交付与分支策略

- 所有实现保留在 `refactoring` 分支。
- Phase 0 提交规范、设计和原型。
- Phase 1–6 每阶段至少一个可回退提交。
- 阶段未通过验证不得进入下一阶段。
- 最终审查完成后再决定是否合并到 `main`。
