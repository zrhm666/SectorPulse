# SectorPulse 现代运营后台前端设计

日期：2026-08-23  
状态：用户已确认设计，等待规格审阅

## 1. 目标

将现有可运行但视觉和信息架构较粗糙的 React 工作台升级为适合单人日常使用的现代运营后台。前端采用浅色界面、清晰卡片、固定侧边导航和一致的状态反馈，同时保留已经验证的后端 API、运行流程、审核治理和 PostgreSQL 数据路径。

本次改造覆盖所有现有前端页面，不只美化首页。实现不得伪造业务数据，不得显示 API Key，不得改变后端分析、审核和发布语义。

## 2. 用户与使用场景

第一版面向单个本机用户，主要在桌面浏览器中使用。用户每天进入系统后需要快速完成以下操作：

1. 判断 PostgreSQL、市场数据 Provider 和 LLM 是否可用。
2. 发起盘中分析或盘后复盘。
3. 查看运行阶段、错误、耗时和成本。
4. 阅读并编辑草稿，核对证据和数字。
5. 通过或退回草稿，并查看治理与版本记录。
6. 管理定时任务。
7. 在需要时查看已暂停的 Phase 3 影子验收状态。

## 3. 设计原则

- 真实数据优先：所有指标和列表来自 API；数据库为空时显示引导式空状态。
- 操作优先：每个页面只突出一个主要操作，次要操作降低视觉权重。
- 状态可解释：运行状态、失败原因、降级原因和下一步操作同时展示。
- 证据优先：审核页面把正文、证据、数字核对和合规判断放在同一工作上下文中。
- 一致性优先：导航、页面标题、卡片、表格、状态标签、表单和反馈由共享组件实现。
- 桌面优先、窄屏可用：主要优化桌面宽屏，同时保证窄屏不重叠、不截断且导航可收起。
- 安全默认：不得渲染 API Key、数据库密码、完整原始 Prompt 或未经脱敏的模型原始响应。

## 4. 技术方案

采用项目现有 React 18、React Router、TypeScript 和 Vite，不引入 Ant Design、MUI 等大型 UI 框架。建立项目自有的轻量设计系统，并逐页重组现有组件。

后端 FastAPI 与 PostgreSQL 仓储保持现有合同。首页汇总优先组合已有 API；只有在无法可靠得出必要状态时，才新增返回脱敏聚合数据的轻量后端接口。

## 5. 应用壳层与导航

新增统一的 `AppShell`，由以下区域组成：

- 左侧导航：产品名称、一级页面入口、当前选中状态和收起控制。
- 顶部栏：当前页面标题、服务状态摘要和当前页面主要操作。
- 主内容区：统一最大宽度、页面间距、背景和响应式行为。
- 全局反馈区：请求失败、操作成功和需要用户处理的配置问题。

一级导航固定为：

| 导航项 | 路由 | 目的 |
|---|---|---|
| 运营总览 | `/` | 查看系统、运行、审核和成本摘要 |
| 分析运行 | `/runs` | 查看、新建和筛选分析运行 |
| 审核工作台 | `/review` | 集中处理待审核草稿 |
| 定时任务 | `/schedules` | 管理盘中、盘后及其他计划 |
| 系统状态 | `/system` | 查看数据库、Provider、LLM 和最近故障 |

保留详情路由：

- `/runs/:runId`
- `/data-runs/:runId`
- `/task-runs/:runId`
- `/shadow-acceptance`

窄屏时侧边栏收起为抽屉或紧凑导航，主内容改为单列。页面功能不得因窄屏而缺失。

## 6. 运营总览

首页采用已确认的“运营总览”布局。

### 6.1 顶部区域

- 页面标题和当前日期。
- 简短系统状态，明确“可运行”“部分降级”或“不可运行”。
- 唯一高强调按钮“新建分析”。

### 6.2 指标卡

展示四个真实指标：

- 今日运行数量。
- 待审核数量。
- 数据源可用数量与总数。
- 本月 LLM 成本。

当后端无法提供指标时，卡片显示“暂不可用”和原因，不显示虚构的零值。

### 6.3 最近运行

展示运行类型、状态、发起时间、耗时和详情入口。无记录时解释这是新数据库，并提供“创建第一次运行”的操作。

### 6.4 今日流程

以“数据采集 → 分析生成 → 人工审核”展示当天最新运行的阶段状态。若当天没有运行，则显示未开始状态和新建入口。

### 6.5 待处理事项与快捷入口

待处理事项仅包含真实需要行动的内容：失败运行、待审核草稿和 Provider 异常。快捷入口包括盘中分析、盘后复盘、审核草稿和管理定时任务。

## 7. 新建分析流程

新建分析采用三步流程：

1. 选择盘中分析或盘后复盘。
2. 确认数据源、截止时间和是否调用真实 LLM。
3. 提交并进入运行详情。

第二步必须明确展示：

- 运行模式。
- 请求截止时间和时区。
- 当前数据 Provider 可用性。
- 当前 LLM Provider 和模型名称，不显示密钥。
- 真实 LLM 可能产生费用的提示。

配置或 consent 缺失时，提交按钮不可用，并显示可执行的修复说明。创建成功后直接导航至对应运行详情，不要求用户回列表查找。

## 8. 分析运行列表

运行列表使用桌面表格和窄屏列表两种布局，支持以下信息：

- 运行类型与模式。
- 当前状态。
- 发起时间与截止时间。
- 运行耗时。
- LLM 成本。
- 进入详情操作。

筛选项限定为状态、运行模式和日期范围。空状态、加载状态和请求失败状态使用共享反馈组件。

## 9. 运行详情

运行详情采用“顶部摘要 + 阶段时间线 + 业务标签页”。

顶部摘要显示运行状态、模式、开始时间、耗时、成本和 cutoff。阶段时间线显示行情、新闻、归因、写作和审核状态。

标签页包括：

- 概览。
- 板块雷达。
- 证据。
- 草稿。
- 审核。
- 治理记录。

失败阶段必须显示失败原因、影响范围和可执行操作。只有后端明确允许重试时才显示重试按钮。

## 10. 审核工作台

审核工作台采用三栏桌面布局：

- 左栏：待审核草稿列表、状态筛选和当前选择。
- 中栏：正文阅读、编辑和版本信息。
- 右栏：证据来源、数字核对、合规检查以及通过或退回操作。

窄屏时三栏变为顺序标签页，保持正文、证据和审核操作均可访问。

编辑保存必须生成新版本，不覆盖历史版本。通过或退回前显示当前版本和审核结论。涉及证据不足、数字不一致或合规风险时，使用醒目但克制的警告区域。

## 11. 定时任务与系统状态

### 11.1 定时任务

页面顶部展示启用计划数量、下一次执行和最近失败。主区域用表格展示计划名称、模式、时区、下次执行、启用状态和操作。创建与编辑表单使用明确字段说明，禁止隐藏时区语义。

### 11.2 系统状态

系统状态页面展示：

- PostgreSQL 连接状态与数据库名称。
- 市场数据和新闻 Provider 状态。
- LLM Provider、模型、超时和预算状态。
- 最近一次成功运行和最近故障。
- consent 文件是否就绪。

页面不得显示 API Key、数据库密码或完整连接串。诊断错误经过脱敏后展示。

## 12. Phase 3 影子验收

保留 `/shadow-acceptance` 页面及现有数据能力。页面顶部固定显示“已暂停”，并解释当前不主动执行 20 个交易日验收。历史真实记录仍可读取；不得为填充进度而创建虚假记录。

## 13. 轻量设计系统

共享组件至少包括：

- `AppShell`
- `SidebarNav`
- `TopBar`
- `PageHeader`
- `StatCard`
- `Panel`
- `StatusBadge`
- `DataTable`
- `EmptyState`
- `InlineAlert`
- `LoadingState`
- `ConfirmDialog`
- 表单字段和主次按钮

颜色、间距、圆角、阴影、字体、层级和状态色通过 CSS 变量统一管理。业务页面不得重复定义卡片边框、按钮颜色或状态色。

## 14. 视觉规范

- 页面背景使用柔和浅灰，主要内容卡片使用白色。
- 主色为克制的蓝色，用于主操作、选中导航和运行进度。
- 成功、警告和失败使用绿、橙和红，并始终搭配文字或图标。
- 圆角与阴影保持轻量，不使用大面积渐变、玻璃效果或装饰动画。
- 中文字体使用系统字体栈；时间、金额和指标使用等宽数字特性。
- 控件保留清晰焦点状态；文本和背景满足可读性要求。
- 动效仅用于导航展开、状态切换和加载反馈，并尊重减少动态效果的系统设置。

## 15. 数据与错误状态

每个数据页面必须实现四种状态：

1. 加载中。
2. 成功且有数据。
3. 成功但无数据。
4. 请求失败。

错误信息区分网络错误、配置缺失、Provider 不可用、数据库错误和业务校验失败。可重试错误提供重试操作；不可重试错误提供配置或诊断入口。操作成功后显示短暂确认反馈，并保持页面数据一致。

## 16. 测试与验收

### 16.1 自动化验证

- 保持所有现有 Vitest 测试通过。
- 新增应用壳层、导航和当前路由选中状态测试。
- 新增首页有数据、空数据、加载和失败状态测试。
- 新增新建分析三步流程和配置阻断测试。
- 新增运行状态、审核操作和系统状态脱敏测试。
- 执行 `npm run test`。
- 执行 `npm run build`。

### 16.2 浏览器验证

- 检查桌面宽屏与窄屏布局，不能出现重叠、截断或不可访问操作。
- 使用空的 PostgreSQL 正式库验证首次使用体验。
- 使用 Fixture Provider 验证从新建运行到查看草稿的完整流程，不消耗真实 LLM 额度。
- 检查键盘导航、可见焦点、表单标签和状态文字。

### 16.3 用户验收

用户在实际浏览器中确认：

- 首页能快速回答系统是否正常、今天是否运行和是否有待审核内容。
- 新建分析流程无需了解内部 JSON 或 API。
- 运行失败时能看到原因和下一步。
- 草稿、证据和审核操作在同一工作上下文中。
- 视觉达到现代浅色运营后台标准。

## 17. 不在本次范围

- 多用户登录、角色和权限管理。
- 自动公开发布。
- Phase 3 真实 20 个交易日运行。
- 移动端原生应用。
- 替换现有 React 技术栈。
- 为展示效果生成虚假业务数据。
