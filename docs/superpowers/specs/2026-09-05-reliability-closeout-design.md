# SectorPulse 可靠性收尾设计

日期：2026-09-05。基线：`main=d2e044d`，工作分支 `codex/stage0-reliability=a5bfc25`。

## 目标与授权

用户已同意审查建议，要求先写设计和计划，再在当前会话执行。继续使用现有隔离工作区，完成缺陷修复、SQLite/PostgreSQL 验收、部署配置和本地 main 集成。无需逐阶段再次确认。远端推送、影子测试恢复、新增业务模块不在本轮范围。

## 方案选择

采用现有设计的定点收尾。相比引入独立任务队列或重写运行系统，这个方案可直接复用已有存储协议和前后端接口，降低迁移风险；只更新文档则无法解决已复现的异常停止和错误状态问题。现有单进程、单用户部署边界保持有效。

## 1. 调度生命周期

将派发和关联任务推进分别置于异常边界内。普通异常只记录异常类型与操作阶段，下一次轮询继续；不得吞掉取消信号，不输出上游异常原文中的凭据。派发失败仍允许已启动任务推进。新增 `is_running` 和 `is_healthy` 只读状态：前者反映后台 Task 存活，后者要求存活且最近轮询没有失败；完整成功轮询清除降级状态。系统就绪接口据此返回 warning/ready，不能以对象存在代替健康。

关闭流程应能处理已经异常结束的后台任务，并始终释放数据库资源。测试须复现一次故障后继续处理，以及降级后恢复。

## 2. 内容运行终态

前端统一包含 READY_FOR_HUMAN_REVIEW、FAILED、CANCELLED、INTERRUPTED、BUDGET_EXCEEDED、ATTRIBUTION_BLOCKED、DRAFT_GENERATION_FAILED、UNREVIEWED、REVISE_REQUIRED 的终态集合。历史终态不订阅 SSE；切换运行时清空旧事件、错误、结束状态；已卸载请求不得更新新页面。中断、未审核和待修订展示具体说明，不推断缺失阶段已经完成。保持现有视觉规范，本轮不改布局。

## 3. 重试来源

数据运行已有 `retry_of_run_id` 字段，须从重试入口传入创建和工作流直至持久化。内容运行通过前向迁移 018 增加可空 `retry_of_run_id` 及索引，旧记录为 NULL。SQLite 和同步 psycopg 仓储都读写来源关系；详情接口返回该字段，兼容旧客户端。新运行创建时一次性存储来源，不采用先创建后补写的竞态方式；旧运行与输入快照不修改。

## 4. 容器运行

基础 Compose 继续支持无授权的 Fixture 使用。增加显式 Live 覆盖文件，将主机已有的 `.live-data-consent` 与 `.live-llm-consent` 作为只读文件挂载，禁用自动创建缺失宿主路径；README 给出明确启动命令。SQLite 服务显式清空 DATABASE_URL，避免继承主机 PostgreSQL 配置。授权是用户已有的明确决定，应用不自动创建授权文件。

## 5. 验收与集成

先完成非 Live 回归，再确认本机 PostgreSQL 服务。业务数据库先备份并验证归档；数据库契约测试使用单独新建的专用测试库，业务库不得作为测试目标。若服务受 Windows 权限阻塞，记录实际阻塞并继续其他独立工作。恢复和迁移的证据必须有执行结果，不能把 CI 配置等同于 CI 已通过。

补充前后端连接实际 API 的 Fixture 验收，验证创建、轮询、草稿查询、审核/导出；无需消耗真实 LLM 或重抓行情。Live 端到端能力若未实际执行应标为待验证。所有本地交付门槛通过后将分支合入 main 并重建主目录前端；门槛受环境阻塞时保留分支并明确说明。旧验收记录修正错误的重试来源声明，并链接本轮最终证据。

## 成功标准

1. 调度异常不永久中止后续周期，状态页能反映降级与恢复。
2. 内容历史终态不会显示正在运行，不保留前一个运行的进度。
3. 两种数据库均保存数据及内容重试来源，旧记录迁移后完整保留。
4. Docker Fixture 与显式 Live 启动配置可解析且数据库选择正确。
5. 验收记录明确测试数量、数据库版本、Fixture/Live 边界和合并状态。
