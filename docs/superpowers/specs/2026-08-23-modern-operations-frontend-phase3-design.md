# Phase 3：分析运行工作台设计规格

日期：2026-08-23  
状态：已自审，可实施  
范围：运行列表、三步新建分析、数据运行详情、内容运行详情

## 1. 目标

Phase 3 要让单人运营者不接触内部 JSON，也能可靠地完成一次分析运行，并在同一套界面中判断“能否启动、运行到哪、失败后怎么办、产物在哪里”。

成功标准：

- Fixture 路径无需真实行情或 LLM，可完整创建运行并进入内容运行详情。
- Live 路径在创建前显示数据库、数据授权、数据源、LLM 配置和 LLM 授权状态。
- 缺少必要条件时不发送创建请求，并给出具体修复位置。
- 运行历史在桌面端为可扫描表格，在窄屏为信息完整的列表。
- 两类运行详情都具备加载、空、错误、运行中和完成状态。
- 内容运行详情提供概览、板块雷达、证据、草稿、审核、治理六个明确入口。

## 2. 体验原则

- 这是高频运营工作台，不是营销页。信息密度适中，状态和操作优先于装饰。
- 页面使用现有浅色精密工作台视觉：单一蓝色主操作、语义状态色、12–16px 圆角、边框分层。
- 新建分析是需要上下文和校验的任务，使用独立页面，不使用模态框。
- 不显示虚构业务数据，不泄露 API Key、Base URL、原始异常或内部输入 JSON。
- 状态文案用中文说明业务影响；保留状态码作为次要技术信息。

## 3. 信息架构

### 3.1 运行历史 `/runs`

页头只保留一个主操作“新建分析”。主体包含：

- 快速过滤：全部、运行中、待审核、已完成、失败；以及 provider 过滤。
- 桌面表格列：状态、运行、Provider、创建时间、耗时、成本、操作。
- 窄屏列表保留相同信息，不依赖横向滚动。
- 空状态直接引导新建分析；加载失败提供刷新操作。

运行编号只显示前八位，但完整编号保留在可访问标签和详情页。

### 3.2 新建分析 `/runs/new`

采用三阶段线性流程，允许返回修改，提交时锁定按钮防止重复：

1. **选择场景**：盘中分析或盘后复盘。说明数据窗口和适用时机。
2. **确认运行条件**：选择 Fixture 演练或 Live 实时运行；展示系统预检结果和缺失项。Fixture 明确标注“不拉取实时行情、不消耗真实 LLM 额度”。
3. **提交分析**：汇总场景、执行方式、候选范围、LLM 使用方式和预计风险，用户执行最终提交。

Fixture 提交调用内置 Fixture 输入和内容运行接口，成功后进入 `/runs/:id`。Live 提交创建数据运行，成功后进入 `/data-runs/:id`。

Live 阻断规则：

- `consent.live_data` 为 false：提示在项目根目录创建 `.live-data-consent`。
- `providers.live_data_available` 为 false：显示后端返回的缺失要求，但不显示敏感值。
- `llm.configured` 为 false：提示检查 `.env` 中 Provider、Base URL、API Key 和 Model。
- `consent.live_llm` 为 false：提示创建 `.live-llm-consent`；因为数据就绪后仍无法生成分析稿，所以在入口提前阻断。

### 3.3 数据运行详情 `/data-runs/:id`

- 顶部摘要：场景、状态、创建时间、候选数量。
- 阶段轨迹：采集、质量校验、候选筛选、归因就绪。
- 质量状态按数据源展示，降级原因使用警告区说明影响。
- 候选板块按排名、评分和理由展示。
- 仅在 `READY_FOR_ATTRIBUTION` 时提供“生成分析稿”。成功后进入内容运行详情。
- 请求失败展示可恢复错误；不直接渲染服务端原始异常。

### 3.4 内容运行详情 `/runs/:id`

- 顶部摘要：状态、Provider、创建时间、耗时、成本、板块数。
- 阶段轨迹：启动、归因、编辑、写作、审核。实时 SSE 更新，历史运行以最终状态补足轨迹。
- 标签顺序：概览、板块雷达、证据、草稿、审核、治理。
- 治理标签复用现有 governance 接口，展示通过状态和问题列表。
- 失败时显示经过前端分类的原因、影响和下一步；不输出原始堆栈或凭据。
- 重试只对已结束、具有输入快照的运行显示。后端详情增加 `retryable` 明确信号，前端不自行猜测。

## 4. 状态与错误文案

状态码通过统一映射输出中文标签，例如：

- `RUNNING`：运行中
- `READY_FOR_ATTRIBUTION`：等待生成分析稿
- `READY_FOR_HUMAN_REVIEW`：等待人工审核
- `COMPLETED`：已完成
- `DEGRADED`：降级完成
- `FAILED`：运行失败

错误按 HTTP 状态和已知错误码分类为：配置缺失、授权缺失、数据未就绪、网络或服务暂不可用、未知错误。界面只展示安全摘要和恢复动作。

## 5. 响应式与无障碍

- 1280px 以上：表格、双栏详情和固定宽度步骤摘要。
- 769–1279px：单栏详情，表格保留。
- 768px 以下：表头隐藏，行转为带字段标签的列表；步骤导航可换行；主操作占满可用宽度。
- 所有状态不能只依赖颜色；按钮有禁用和忙碌文案；标签页使用 `tablist/tab/tabpanel` 语义。
- 键盘焦点清晰，动态错误使用 `role="alert"`，加载状态使用 `aria-live`。

## 6. 数据合同调整

后端 `RunDetail` 增加：

```json
{ "retryable": true }
```

计算规则与重试命令一致：运行不存在、正在运行或没有输入快照时为 false，其余为 true。列表不需要该字段。

## 7. 明确不做

- 不恢复 JSON 文本框或文件上传入口。
- 不在 Phase 3 新增账号、权限或多租户。
- 不把影子验收重新开启。
- 不自动创建 consent 文件或修改 `.env`。
- 不在前端显示 API Key、Base URL 或原始后端异常。

## 8. 自审结论

本规格覆盖总计划中 Phase 3 的列表、三步创建、预检阻断、两类详情、失败恢复、治理入口和 Fixture 闭环。交互不依赖新 UI 框架，后端只需增加一个可重试能力字段，改动边界清晰，可以进入实施。
