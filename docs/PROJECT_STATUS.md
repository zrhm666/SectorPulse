已交付的边界：权威状态在 PostgreSQL，Milvus 只是可重建的派生索引；A3/A4 只能读 A2 已接纳的引用；不自动推断文档版本；不解析原始文档的二次引用图。

**冲突这一条的保险在哪，需要说清楚。** 设计上 NLI 判不了的冲突必须记为 `UNRESOLVED`，服务端也确实会拒绝引用同一个切片的 `UNRESOLVED`；但给出这个判定的不是系统的裁决链（见下），而是调用方。`UNRESOLVED` 被拦得住的情形很窄，`RESOLVED` 则完全不校验。

已知缺口：每类 RAG Provider 的 base URL 与 API Key 在配置层还没有归属（冒烟与端到端用例暂时借用 `SECTOR_PULSE_LLM_BASE_URL` / `_API_KEY`）；仓库还没有生产级的 MinIO/Milvus/LLM 组合装配器；PostgreSQL outbox 的重放契约尚未对真实 PostgreSQL 验证过。

**本节不能作为"RAG 已可用"的证据引用。**

另外，逐节核对设计规格后确认有四处是**规格要求了、实现没有做**——这与验收跳过是两件事，真机跑通那些用例也不会发现它们：阈值告警（§20.3）、Embedding 升级时的集合别名切换与回滚窗口（§16.5）、可选的查询改写 Provider（§11.2）、解析器的受限 worker 隔离（§18.1）。详见实施计划文末 E157。

2026-09-18 又在 20 个任务全部完成之后补做了一次代码审查（同一份实施计划里记作 E158～E170）：对累计 diff 做了只读审查，报告里的每一条都回到代码里复核过，复核不成立的不写入。结果是修掉 10 处、记录 2 类架构缺口，**未提交任何改动**。审查后重跑门禁：Ruff 通过、Mypy 362 个文件通过、前端 288 项通过（新增 2 条）、构建与工具链 4 项通过。

**必须知道的第一条：已接纳证据的读取端在真实 PostgreSQL 上必然抛 `TypeError`。** 迁移 035 之后那三列是 JSONB，psycopg 3 直接返回 Python 对象，而读取端写的是无条件 `json.loads`；SQLite 夹具读的正是 TEXT，所以这条离线永远看不见，而 PostgreSQL 是 RAG 唯一的生产装配。修法是把读法提成一处共享规则，并加了一条驱动形状的离线用例（`backend/tests/unit/storage/postgres/test_research_evidence_jsonb.py`）。另外九处——四个维护端点漏了错误映射、空 actor 报成 500、维护接口把对象存储键交回浏览器、重放会继续递交已撤回的正文、上传幂等分支谎报 `has_source`、前端提前回收 blob URL，以及两条对任何实现都成立的测试断言——见 E159～E166。

**必须知道的第二条：冲突裁决链没有接进运行时。** `ClaimExtractionService`、`ConflictService` 与规则裁决都已实现、单测通过，但没有任何生产装配会构造它们（`runtime_bundle` 与依赖注入里对 claim / conflict 零引用）。今天 `conflict_status` 是模型调用 Tool 时的必填参数，服务端只校验两件窄事：`CHECK_FAILED` 要带 `requires_verification`，`UNRESOLVED` 要引用两个不同切片。所以两条独立等权文档必须停在 UNRESOLVED 这条保证，目前靠调用方守规矩，不是系统拦着——**真机跑通前述用例也不会发现这一点**。详见 E167。

还有六项已核实、本轮未修的缺陷（Provider 预算与配额尚未参与决策、Milvus re-stage 会把 PUBLISHED 写回 STAGED、保留期清理只清权威库的行而原件留在对象存储、同一个 `upload_key` 重放产生孤儿文档、purge 可重复执行且 restore 不认 PURGED、派生索引把一页当全量）。它们都需要真实基础设施才能验证或验收，因此记录而非改动，详见 E168。
